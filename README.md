# レモンスコア

メロンソーダに入れたレモンポーションの個数を当てるゲームを、スマートフォンから記録・進行・集計するWebアプリ。
仕様は [lemon-score-spec.md](lemon-score-spec.md)（版0.3）。この実装は第1段階の範囲。

## 技術構成

| 項目 | 採用 | 理由 |
| --- | --- | --- |
| 実行環境 | Node.js 24以上（開発は v26） | 追加ランタイム不要。`node:sqlite` が標準で使える |
| サーバー | `node:http`（フレームワークなし） | 依存を減らし、自前サーバーでの更新を簡単にする |
| DB | SQLite（`node:sqlite`、WALモード） | 1ファイルで永続化・バックアップが容易。DBをネットワークに公開しない |
| 画面 | 素のHTML/CSS/JavaScript（ビルド不要） | `public/` をそのまま配信 |
| 外部依存 | `qrcode` のみ | 招待URLのQR生成（サーバー側でSVG化） |
| テスト | `node:test` | 権限・状態遷移・競合・集計をAPI経由で検証 |

```
src/
  main.js        起動・定期削除
  server.js      HTTP、Cookie、CSRF、試行制限、ルーティング、静的配信
  game.js        権限・状態遷移・秘匿・復帰（ここが中心）
  stats.js       集計・結果テキスト
  db.js          スキーマ・トランザクション
  config.js      環境変数
public/          画面（index.html / app.js / style.css）
test/            自動テスト
deploy/          systemd・リバースプロキシ・バックアップの例
```

## 起動

```bash
npm install
```

開発（http://localhost:3100、Cookieの Secure なし、`./data/dev.sqlite`。ポートは `PORT=` で変更可）:

```bash
npm run dev
```

テスト:

```bash
npm test
```

本番: `.env.example` を参考に環境変数を設定して `npm start`（`.env` があれば読み込む）。
詳細は [docs/operations.md](docs/operations.md)。

## 画面上の呼び方

仕様書の A・B は画面に出さない。A＝**飲む人**、B＝**入れる人**と表示する（結果テキストも「飲む人：たろう」）。
コード・API内部の `role` は引き続き `A` / `B`。

## 秘匿の仕組み（第9章）

- 状態取得 `GET /api/rooms/:id/state` は、役割に関係なく**実投入数・予想数・正誤・集計値を一切含めない**。返すのは状態・杯番号・当番・確定有無・完了杯数・版番号のみ。
- 本人の値は専用の `GET /api/rooms/:id/mine` だけで返す（Bは自分が担当した杯の実投入数、Aは自分の予想）。
- 結果 `GET /api/rooms/:id/result` と JSON書き出しは `FINISHED` になるまで、A・B・進行役の誰が呼んでも 403。
- 進行役は飲む人／入れる人とは別の属性で、数値の閲覧権限は増えない（進行役が飲む人でも同じ制限）。
- 参加者はCookieのセッションで毎回サーバー側で引き直し、クライアントが送る role / member_id は使わない。
- DB行をそのまま返さず、`game.js` で役割別にレスポンスを組み立てる。
- 保護APIは `Cache-Control: no-store`。Service Worker は置かない。

## API概要

| メソッド・パス | 内容 |
| --- | --- |
| `POST /api/rooms` | 部屋作成（作成者＝進行役） |
| `POST /api/invite` | 招待トークンから部屋を解決（最小限の情報のみ） |
| `POST /api/rooms/:id/join` | 参加申請 |
| `POST /api/rooms/:id/members/{approve,reject,remove}` | 参加の承認・拒否・取消（進行役、LOBBY） |
| `POST /api/rooms/:id/order` | Bの順番変更（進行役、LOBBY） |
| `POST /api/rooms/:id/start` | 開始 |
| `GET  /api/rooms/:id/state` | 状態取得（役割別） |
| `POST /api/rooms/:id/actual` / `actual/correct` | 実投入の確定／予想確定前の訂正（版番号を検証） |
| `POST /api/rooms/:id/guess` | 予想の確定（版番号を検証） |
| `POST /api/rooms/:id/fatigue` | 疲れ具合（Aのみ、任意） |
| `POST /api/rooms/:id/{skip,void,pause,resume,finish}` | 進行役の操作 |
| `GET  /api/rooms/:id/mine` | 本人の値だけ |
| `GET  /api/rooms/:id/result` / `export.json` | 結果・JSON（終了後のみ） |
| `GET  /api/rooms/:id/recovery/names` | 復帰用の表示名一覧（表示名のみ） |
| `POST /api/rooms/:id/recovery` / `GET recovery/status` | 復帰申請・待機（承認後に新セッション発行） |
| `POST /api/rooms/:id/recovery/decide` | 復帰の許可・拒否（本人以外の参加者なら誰でも） |
| `POST /api/rooms/:id/delete` | 終了した部屋の削除（進行役） |
| `GET  /api/my-rooms` | この端末で参加した保存期間内のゲーム |

状態を変える入力（start / actual / correct / guess / skip / void / pause / resume / finish）は `request_id` 必須。
同じIDと同じ内容の再送は最初の結果を返し、同じIDで別内容なら 409。

POST はすべて `Content-Type: application/json` と `X-LS-CSRF: 1` ヘッダーが必要（CSRF対策。Origin も照合）。

## 仕様からの補足・解釈（変更点の明示）

仕様のルールや公開範囲は変えていない。未指定だった細部は次のように決めた。

1. **準備待ち（WAIT_ACTUAL）の杯はDBに行を作らない。** 実投入が確定した時点で杯番号を採番する。これで「空の準備枠は杯番号を消費しない」「空の準備待ちで終了しても結果に混ざらない」を構造的に満たす。画面上は「第n杯・担当○○・実投入待ち」と表示する。
2. **無効理由は、終了前は進行役だけに返す。** 理由の文に数値が書かれてもA等へ漏れないようにするため。終了後は全員に公開。
3. **開始時に未承認の参加申請は自動で拒否**する（開始後は新規参加を止めるため）。
4. **開始前の参加取消**（進行役が承認済み参加者を外す）を用意した（8.1「参加の承認・取消」）。
6. **結果テキストの日時は開始日時**（未開始なら作成日時）。予想の偏りが0のときは「0個（偏りなし）」、正なら「＋0.2個（多め）」。
5. **入れる人の実投入数は、Aの予想確定前なら「自分が入れた個数を見る」から訂正できる**（8.2）。訂正履歴はJSON書き出しに含める。

## 復帰の仕組み（仕様 6.1.1 / 12.3 / 12.4 からの変更）

1. 同じブラウザで招待URLを開き直すと、Cookieで自動的に戻る（変更なし）。
2. 戻れないときは、招待URLを開くと参加者の名前が並ぶ（開始後はこの画面だけ。開始前は参加フォームの下）。
3. 自分の名前をタップすると、**本人以外の参加者全員**の画面に「○○さんが別の画面から戻ろうとしています［許可］［拒否］」が出る。
4. 誰か1人が「許可」を押すと、元の役割・順番・入力のまま戻る。古いブラウザの認証は無効になる。

仕様からの変更点：

- 許可できるのは「進行役（進行役本人の復帰だけは他の参加者）」→ **本人以外の参加者なら誰でも**。
- **申請番号は廃止。** 同じ人への申請は最新の1件だけを残し、古い申請は自動で失効させて取り違えを防ぐ。
- **進行役の予備の復帰リンクは廃止。** 進行役も他の人と同じ方法で戻れるため。
- 変わらない点：名前のタップだけでは認証しない／許可前は何も見えない／本人は自分の申請を許可できない／申請は10分で失効／全員が戻れなくなった場合は復元できない。

## 既知の制限

- **1プロセスで動かす前提。** 排他は SQLite の `BEGIN IMMEDIATE` で行うが、試行制限はメモリ内のため、複数プロセスにすると制限が分散する。
- 状態反映は2.5秒間隔のポーリング（画面に戻ったとき・オンライン復帰時は即時取得）。
- PWA（ホーム画面追加・オフライン）は未実装（任意項目）。
- 試行制限は同じIPの人をまとめて数える。同じWi-Fi（同じグローバルIP）から大人数で同時に操作する場合は `RATE_LIMIT_PER_MINUTE` を上げる。
- LINE内ブラウザの認証情報は外部ブラウザへ引き継がない（仕様どおり）。引き継げない場合は「ゲームに戻る」から承認付きで復帰する。
- 全員が認証情報を失った場合は復帰できない（許可できる人がいないため。新しい部屋で続ける）。
